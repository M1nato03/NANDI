# A year of data on a slow phone (cloud job 9, batch 2)

Branch measured: `origin/ship-27` @ `b17ec40`. Report branch: `ideas/cj2-heavy-data`.
Date: 22 Oct 2026. No app code was changed. Scripts, backups and profiles stayed in `/tmp`; the key code is below.

## Headline

- **With a year of data the Plan screen keeps the phone's CPU busy even when nobody touches it.**
  At 6x CPU throttle, idle Plan used 8% of the main thread at 30 days, 21% at 180 days and **~100% at 365 days**.
  The cause is one quadratic line, `src/core/tasks/complete.ts:15`, re-run on every render. Plan re-renders every second from the 1 s clock in `src/ui/tasks/useTaskBoard.ts:29`.
- **Each write sets off a cascade.** Finishing a task, answering a question or the once-a-minute app-time write re-reads whole tables in 6 or more live queries. It then runs `deriveEconomy` 3 or 4 times and a full `reconcileGamify`.
  At 365 days a task tap took **9 s** to show the ticked row (2.2 s at 30 days). A Learn answer caused **4.7 s** of main-thread work after the tap (0.5 s at 30 days).
- **What stays fast:** the Learn feedback sheet (about 0.1 s at every size, because it is set before the write) and tab switches (under 0.1 s to swap). The app shell also paints in about 2.3 s at every size.

## Why it gets slower: profiles and causes

Method:
- I made a separate source-mapped build (`vite build --sourcemap`, served on port 5339, same code).
- I seeded it the same way and took one run with the CDP sampling profiler around each step.
- I aggregated self and inclusive time by original `src/` file:line.
- I timed the pure functions in Node on the same data, unthrottled, median of 15. The "~6x on the phone" figures are an **estimate** (6 × Node).

### Causes, with file:line

1. **Quadratic Now-task pick, run every second.**
   - The cause: `src/core/tasks/complete.ts:15`, `open = tasks.filter(task => … && !tasks.some(child => child.parentId === task.id))` scans all tasks once for every open task. It also calls `dayKey(now)` inside the filter at line 16.
   - The trigger: `src/ui/screens/Plan.tsx:61` calls it on every render. `src/ui/tasks/useTaskBoard.ts:29` re-renders Plan every 1 s.
   - The cost: about 27 ms per call unthrottled at 365 days, about 165 ms at 6x (estimate). This alone keeps idle Plan busy and slows every Plan update.
   - Fix: build a `Set` of `parentId`s once, which makes the scan linear. Hoist `dayKey(now)`.
2. **The 1 s clock re-renders all of Plan.**
   - The clock: `src/ui/tasks/useTaskBoard.ts:29` (`setInterval(refresh, 1000)` → `setNow`).
   - Plan then recomputes the following over every task on each tick: `taskGroups` (Plan.tsx:44), `adaptiveNight` (:46), `chooseNowTask` (:61), `needsFreshStart` (:72), `steadyLine`, and the TaskList render.
   - Fix: tick only while a focus timer runs, or put the clock in the timer component. Wrap the derived lists in `useMemo([tasks, focus, today])`.
3. **EconomyFeedback reads whole tables and derives twice on every change.**
   - `src/ui/shell/EconomyFeedback.tsx:32` reads all of `ledger`, `settings`, `tasks`, `sessions`, `puzzleRuns` and `learnConcepts` whenever any of them changes.
   - Lines 116-117 run `deriveEconomy` **twice** (old and new view) **before** the early return at the `!achievement && !dropFinished && !justCompleted` check. So a change with nothing to celebrate still pays for two derives.
   - Line 67 runs `reconcileGamify` on every change.
   - It is mounted on every screen.
   - Fix: return early before deriving. Derive once and keep the previous view in a ref. Debounce the reconcile.
4. **`reconcileGamify` does full scans on every write.**
   - `src/data/repos/gamify.ts:19` reads the whole ledger. Line 37 reads all settings.
   - Line 38 runs a full `deriveEconomy` just to check for today's welcome gift.
   - Line 44, `for (let tier = 1; tier <= badgeTier(badge, facts); tier++)`, calls `badgeTier` again in the loop condition. `badgeTier` (`src/core/economy/gamify.ts:90`) calls `badge.count(facts)` once per threshold, and each count filters the whole ledger (`all`, gamify.ts:64). That is up to about 250 full ledger scans per reconcile.
   - Its own writes trigger the live queries again, so it runs at least twice per user action.
   - Fix: compute each badge count once. Skip the badge and welcome passes when no new fact arrived since the last pass. Only read today's facts where possible.
5. **The once-a-minute app-time write triggers the whole cascade in idle.**
   - `src/ui/shell/useForegroundMinutes.ts:44` (15 s tick) calls `addAppMinutes` (`src/data/repos/guard.ts:8-14`), which writes `dailyLog` every minute.
   - That write wakes EconomyFeedback (it reads `dailyLog.get(today)`), so items 3 and 4 run. It also wakes TodayDots and the full `dailyLog` reads in Plan.
   - In the 65 s idle profile at 365 days this cost about 2 s of CPU, every minute, with no user action.
   - Fix: flush app minutes on `visibilitychange` / `pagehide`, or store them where no always-mounted query watches.
6. **Several always-mounted readers load the same whole tables.**
   - On Plan, the ledger is read in full by `TodayDots` (`src/ui/shell/TodayDots.tsx:21-28`, which also reads tasks, sessions and puzzleRuns), EconomyFeedback, `useCourtyard` (`src/ui/courtyard/Courtyard.tsx:24-28`, the 12 courtyard kinds, most of the ledger) and `reconcileGamify`.
   - Plan also loads all `taskEvents` (`src/ui/screens/Plan.tsx:42`, 4.6k rows at 365 days) just to pass them to `TaskDetail` when it opens.
   - TodayDots only needs today's facts: use `ledger.where('dayKey').equals(today)` and `tasks.where('dayKey')`.
   - Fix: load events inside `TaskDetail`. Share one economy source, a context or store that derives once per change, across EconomyFeedback, TodayDots, YourSeason, Hexagon and DailyQuests.
7. **You and Learn re-read and re-derive.**
   - `src/ui/screens/You.tsx:16-21` reads 7 whole tables.
   - `YourSeason` → `useEconomy` (`src/ui/screens/EconomyScreens.tsx:21-23`) reads ledger and settings and calls `deriveEconomy` on **every render**, with no memo.
   - `HexagonCard` (`src/ui/screens/HexagonCard.tsx:16-20`) reads 8 tables including all taskEvents. `hexagon` then calls `deriveEconomy` again (`src/core/hexagon.ts:92`).
   - `DailyQuests` (`src/ui/screens/GamifyScreens.tsx:11-13`) reads the ledger and re-renders every 1 s, scanning it each time.
   - `Learn` (`src/ui/screens/Learn.tsx:31-39`) reads the whole ledger plus the engine facts. `LearnDrop` (`src/ui/learn/LearnDrop.tsx:34-44`) reads every saved drop (287 at 365 days).
8. **`deriveEconomy` itself is linear but heavy.**
   - It sorts a copy of all facts each call (`src/core/economy/deriveEconomy.ts:59`) and walks every day since the first fact. That costs about 15 ms unthrottled at 365 days (about 90 ms at 6x, estimate).
   - It runs 3 to 5 times per user action (items 3, 4, 7). The ledger is append-only and past days are closed, so a cached per-day result for closed days would make it nearly constant. Job 2's `day-close` branch is aiming at this.

Expected effect, an **estimate** I did not measure:
- Item 1 alone should cut idle Plan from about 100% to roughly the 180-day level or lower, and the task tap by several seconds at 365 days.
- Items 3 to 5 should cut the Learn answer cascade (4.7 s) by more than half.
- Check with the same script after each change.

## Caveats

- **Synthetic data.**
  - Unfinished tasks were left alone, so `tasks.reconcile` moved them to `someday`: 513 of 1,647 tasks at 365 days. A tidier user has fewer open tasks, which shrinks `chooseNowTask`'s outer loop, but done tasks are still scanned in the inner `some`.
  - No mystery cases, deck cards or lessons from Mind. The Season (starts 2 Nov 2026) is not active on 22 Oct, so season maths was cheap here and may cost more after 2 Nov.
- **Not a phone.**
  - Headless desktop Chromium with 6x CPU throttle on a shared 4-CPU server. There is no GPU, and IndexedDB disk speed is the server's.
  - Android WebView on a budget phone may differ, especially IDB and storage speed. Treat the trend and the ratios as solid, and the absolute ms as indicative.
- **Time zone.** Pacific/Honolulu was used so the whole session stayed inside one daytime `dayKey`, away from the shutdown and night routes. India time would have hit the night route mid-session. The day boundary logic is the same.
- Cold open uses the service-worker cache, which is close to how the installed Android build loads local assets.
- Profiling adds overhead: the 365-day profiled cold open showed Today at 15 s against an unprofiled median of 7.9 s. Use profile numbers as shares, not as latencies.

await train.completeOnboarding({ track: 'bodyweight', days: [1, 3, 5], weeklyTarget: 3, restDay: 0, equipment: {...}, heatModeEnabled: false, placement: { squat: 2, push: 2 } }, Date.now());

  for (let k = 0; k < 4 + Math.floor(rnd() * 3); k++)             // 4-6 tasks, 2 Musts, every 90 min from 09:00
